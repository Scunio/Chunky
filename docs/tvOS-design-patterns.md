# tvOS design patterns — confirmed the hard way

Rules below were each confirmed by direct evidence (screenshot, crash log, or compile error), not guessed. Keep this updated whenever a new one is confirmed; don't add speculative entries.

## Focus / input

**`.onMoveCommand` swallows unhandled directions — it does not fall through to the system focus engine.**
A `switch direction { case .left: ...; case .right: ...; default: break }` means pressing up/down on that focused view does *nothing* — focus does not move to sibling views (e.g. a header above a full-screen focusable page). To let focus travel in an unhandled direction, explicitly release it: set the bound `@FocusState` to `false` in that case. Confirmed in `ReaderView.swift`'s `tvOSPager`, where up/down were dead until an explicit `case .up: isPagerFocused = false` was added.

**A focusable view underneath a modal/overlay keeps receiving input unless explicitly disabled.**
Presenting a dialog as a plain `ZStack` overlay (not a `.sheet`) does not automatically defocus or disable whatever was focused before it appeared. If the view underneath still has `.focusable(true)` and its own `.onMoveCommand`, remote input keeps going there instead of to the dialog's buttons. Fix: condition `.focusable(...)` on whether the dialog is presented, and explicitly restore focus to the underlying view when the dialog is dismissed (in every dismissal path — cancel, confirm, etc.).
This isn't just a reader-chrome issue: `ChunkyApp.swift` overlaid the parental-lock screen the same way, opaque `.background` but no `.disabled(lock.isLocked)` on `ContentView` underneath — an opaque background hides content visually but doesn't stop tvOS's remote focus from reaching it. Same fix: `.disabled(lock.isLocked)` on the view being covered.

**`.buttonStyle(.automatic)` already draws its own resting-state rounded background on a focusable icon-only button.**
Adding a custom `Circle()`/`Capsule()` `.background(...)` on top produces two visibly nested shapes (small circle chip floating inside the system's own larger rounded-rect backdrop), not one clean pill. If you want a native focus ring/scale, size the content with `.frame(...)` only and let `.automatic` supply the background — don't also add your own. Confirmed via cropped Canvas screenshots on `ReaderView.swift`'s header icons and the "Libreria" back pill.

**A tvOS `List` row's own focus-highlight shape is a `Capsule`, not a rounded rectangle.**
A `12pt`-cornerRadius `RoundedRectangle` background for the rest state visibly changes shape when the row gains system focus. Match the system's own shape: use `Capsule()` for a row's rest-state background (`tvOSRowBackground()` in `TVPanel.swift`).

**`DisclosureGroup` is unavailable on tvOS — even in code never referenced from a tvOS-only code path.**
Swift still type-checks it, so it must be wrapped in `#if !os(tvOS)` explicitly, not just left unused by tvOS-specific branches.

**`NavigationStack` cannot be nested.** A view pushed inside an existing `NavigationStack` must not wrap its own body in a second one.

## Layout

**`.navigationTitle` renders as an overlay at a fixed screen position on tvOS, not a sticky scrolling header.**
A long enough list scrolls straight through it. Put the title in the view's own layout (a `Text` at the top of a `VStack`) instead, and hide the system one with `.navigationTitle("")` + `.toolbar(.hidden, for: .navigationBar)`.

**tvOS HIG safe-area margin is ~80pt horizontal**, not the 10pt shared with iOS/macOS bars — every tvOS-specific chrome edit in this app uses `.padding(.horizontal, 80)`.

## Core Data / Previews

**`NSPersistentContainer`/`NSPersistentCloudKitContainer` resolve their model via `Bundle.main` by default — this breaks under Xcode's Previews/`RunCodeSnippet` JIT execution.**
In that execution mode `Bundle.main` resolves to the injected preview dylib wrapper, not the bundle actually containing the `.momd`, so the container silently loads zero entities and every fetch crashes with "must have an entity." Fix at the production-code level (not a preview-only workaround): resolve the model explicitly via `Bundle(for: AnchorClass.self)` (an anchor class defined purely to be that lookup target) and pass it to `NSPersistentCloudKitContainer(name:managedObjectModel:)`. A normal app launch behaves identically either way, so this isn't a preview-only special case. See `PersistenceController.swift`.

**Xcode Canvas (`PreviewShell`) can crash on its own, unrelated to app code.**
Seen: an infinite recursion inside `UIAccessibility`/`UIKitCore`'s focus/accessibility-tree walker (`isAccessibilityElement` / `canBecomeFocused` calling each other thousands of times → stack-guard segfault), zero frames from app code in the stack. Confirmed as a flake, not reproducible via `RenderPreview` immediately after. If it recurs: close/reopen the Canvas panel, or just retry the render — don't assume it's a bug in the view being previewed without reproducing it via `RenderPreview` first.

## Verification method

A static Canvas/`RenderPreview` screenshot only shows one frame's visual state — it cannot catch focus-navigation or input-routing bugs (e.g. the `.onMoveCommand` issue above), which need real directional input (simulator or device) to surface. Don't treat "renders correctly in Canvas" as "works correctly with a remote."

**tvOS Simulator via xcodebuildmcp: how to actually drive it.** `tap`/coordinate-based actions can fail with an orientation-probe error on tvOS (`Unable to determine rotated simulator orientation`) even though the app itself never rotates — it's the automation layer, not a real bug (confirmed: `open_sim` doesn't fix it either, it's a structural tvOS limitation of that tool's orientation probe, not a transient state to reset). Use `key_press` with HID keycodes instead: 79/80/81/82 = right/left/down/up (the D-pad), 40 = select, 41 = Menu/back. This reliably drives real tvOS focus navigation. **Correction, found later the same night:** an earlier version of this note claimed a `TabView`'s tabs switch content as soon as focus *moves* onto them, no `select` needed — not confirmed for this app's plain (non-`.sidebarAdaptable`) `TabView`. A temporary debug print in the destination view's body showed it *not* evaluating while focus merely rested on the tab in some reproductions, and only evaluating after an explicit `select` in others — inconsistent enough that the claim shouldn't be trusted either way. Always commit with an explicit `select` and confirm via a debug print or the destination's own known-good data (not just a focus-move + screenshot) before reading a tab's content as ground truth. Seed a real library entry first with the `--uitesting-seed` launch arg (`UITestSeed.swift`) — the library is otherwise empty in a fresh simulator and there's no file picker to import one by hand. Screenshots can occasionally show a stale/cached frame after a navigation transition (confirmed: two consecutive screenshots showed the old screen while the accessibility snapshot's element list already reflected the new one) — when screenshot and snapshot disagree, trust the accessibility snapshot (`snapshot_ui`), it reflects the live view hierarchy, not a rendered frame. The reverse also happens: `snapshot_ui` can list the same label twice (e.g. two "Downloads" entries) for a `List` row that a screenshot confirms appears only once — a stale node left over from before a scroll/focus change, not a real duplicate row; cross-check against a screenshot before treating a snapshot-only duplicate as a bug. Blind multi-step key navigation without a screenshot after each step is unreliable this way — a `select` can land on the wrong element if a prior step's target was ambiguous; screenshot to confirm current focus before a consequential key press (e.g. before `select`).

**A `Form`/`Section` with a footer on tvOS renders as one full-bleed rounded card spanning the row(s) plus the footer caption**, not a per-row pill with separate footer text below it — confirmed by comparing rest vs. focus state (same shape both times, only brightness differs). Don't mistake this for the nested-shape bug: it's consistent Apple system styling for `Form`, not a custom background layered under `.automatic`/`.card`.

**RESOLVED — two compounding causes, both found by reading `print()` output from `xcodebuildmcp`'s `runtimeLogPath` rather than inferring from screenshots.**

1. `.onMoveCommand` keeps receiving directional events as long as the view stays `.focusable`, independent of any `@FocusState` binding's *value* elsewhere. Just reassigning a `Bool`/enum binding on Up and hoping the system re-targets focus isn't enough — confirmed the pager's `onMoveCommand` closure still fired for `right` after its binding had "moved," and a real 3-second gap ruled out a timing race. Fix: make `.focusable` on the view you're leaving *itself* depend on where focus should be, forcing a real UIKit focus hand-off (see the code sample below).
2. Once (1) is fixed, **every focusable view in the group needs its own case and its own `.focused($x, equals:)` binding** — not just one binding on the first button. With only the first button (Libreria) bound, moving focus (via ordinary system navigation) to a second, unbound button made the shared `@FocusState` revert to `nil` (nothing currently matched either known case) — which flipped the pager's `.focusable` condition back to `true` while focus was still legitimately elsewhere, re-enabling `.onMoveCommand`/the tap gesture underneath whatever the user was actually doing. Fix: give each navigable target (search, novità, ora-in-lettura, account, layout-cycle, …) its own enum case and its own `.focused(...)` binding, so the tracked value never goes ambiguous while focus is anywhere in that group.

```swift
private enum ReaderFocusTarget: Hashable { case pager, libreria, search, newComics, nowReading, account, layout }
@FocusState private var readerFocus: ReaderFocusTarget?
private var isPagerFocusable: Bool {
    (readerFocus == nil || readerFocus == .pager) && !(/* dialog conditions */)
}
// pager: .focusable(isPagerFocusable) .focused($readerFocus, equals: .pager)
//        .onMoveCommand { if $0 == .up { readerFocus = .libreria } }
// EVERY header button: .focused($readerFocus, equals: .thatButtonsCase)
```

**Testing caveat, not an app bug:** scripted `key_press` sequences need noticeably more settle time between a directional move and the following `select` than a real remote press does — under ~1.5s gaps intermittently produced stale reads (the previous focus target's action firing, or nothing firing) even on this fully-fixed code; a consistent 2–3s gap before a consequential `select` reproduced correctly every time. Don't mistake this for a focus bug — cross-check with a longer delay before concluding real navigation is broken. Confirmed again later the same night: a page-turn that looked "stuck" for 5 consecutive presses turned out to be `step()` never even being called (checked via the same print+log method) — every one of those presses was silently dropped by the simulator's key injection, not a real bug.

**Testing caveat, mirror image of the dropped-key issue:** a single `key_press` directional move (e.g. right, keycode 79) from the library grid's top cell was seen opening that comic's detail screen outright — as if `select` had fired too — reproduced 3x independently from a fresh launch. Before accepting this as a real bug, read the actual navigation code: `LibraryView.swift`'s `ComicCell`/grid has no `.onMoveCommand`, no `@FocusState`-driven `navigationDestination`, no `selection:` binding, and no overlapping/invisible tappable element next to a cell — the only path to `TVComicDetailView` is `Button(action:)` → `handleTap(on:)` → `detailComic = comic`, i.e. a real select. With that path confirmed absent, a directional key spuriously producing a select's effect points at the simulator's HID/AXe injection layer coalescing two events into one delivery — the inverse of the already-documented dropped-key quirk, not a new app bug. Confirm the same way each time: check the actual code for a wiring path before blaming the app, don't just assume from the symptom.

**A section unconditionally shown at the top of `libraryGrid` bled non-favorite comics into the Preferiti tab.** `LibraryView.swift`'s tvOS-only "Novità" (recent-comics) section was added at the top of `libraryGrid` unconditionally (`if !recentComics.isEmpty`) as a substitute for having no separate "New" tab — reasonable for the main "Libreria" tab, but the same `LibraryView` struct is reused for the "Preferiti" tab via `LibraryView(selection: .favorites)`, and `recentComics` has nothing to do with `effectiveSelection`/favorites. Live testing showed the Preferiti tab listing several non-favorite comics — looked exactly like a broken favorites filter. Root-caused with a temporary debug print in `filteredComics` (not a screenshot): it showed `filteredComics` computing the correct 1-item favorites-only result the whole time, while the visibly-rendered grid still showed many more comics — proving the extra comics came from a different code path entirely, not a filter bug. Grepping the view for what else renders comics found the "Novità" section immediately. Fixed by gating it to `effectiveSelection == .all`. **Lesson: when a screen shows more/wrong data than its own filter logic should allow, check for a second, unconditionally-shown section sharing the same screen before assuming the filter itself is broken** — a debug print on the suspected filter is what proved it wasn't the filter, redirecting the search to the right place in one step instead of an open-ended grep.

**Hidden nav bar at every level of a pushed stack breaks Menu's pop.** `TVComicDetailView` is pushed from the library grid via `.navigationDestination(item:)` inside the tab's own `NavigationStack` — a normal push, not a nested-stack or sheet mistake. But both the grid (`LibraryView`) and the detail screen hide their nav bar (`.navigationTitle(""); .toolbar(.hidden, for: .navigationBar)`, the standard in-layout-title pattern documented above). With no visible bar/back-affordance at *any* level, tvOS's Menu button had nothing to base a "pop one level" decision on and fell straight through to its outermost default: exit the whole app to the Home Screen, skipping the grid entirely — reproduced live twice. Fixed by not relying on that inferred default at all: an explicit `.onExitCommand { dismiss() }` on `TVComicDetailView` pops the stack directly via `@Environment(\.dismiss)`. Same lesson as the reader's focus-state fixes elsewhere in this doc — don't trust tvOS's implicit default behavior once you've hidden the chrome it normally uses to make that decision; drive the outcome explicitly instead.

**Testing caveat, correction: a single `Right` press from a fresh app launch reliably reaches and cycles through the tab bar.** The below note ("reaching the tab-bar sidebar... is unreliable") holds for navigating back to the sidebar from *deep* inside a tab's content after other navigation — but starting from a **fresh launch**, with focus still on the grid's top-left cell, a single `key_press` `Right` (keycode 79) reliably jumped straight to the tab bar and *selected* the next tab (each `Right` both moves and activates one tab over: Libreria → In lettura → Preferiti → Account → Impostazioni, confirmed live across multiple consecutive presses in one session). `Down`/`Left` within the tab bar itself did not reliably move between tab items once landed on one — only repeated `Right` from a fresh launch was reliable. If a future session needs the Account tab (or any other), relaunch the app and press `Right` the needed number of times rather than trying to escape the grid after other navigation has happened.

**Testing caveat: reaching the tab-bar sidebar via scripted `key_press` from deep in the library grid is unreliable.** `Left` reliably moves focus from the tab bar into the grid (confirmed repeatedly). The reverse — `Right`/`Up` from within the grid back to the sidebar — did not reproduce reliably this session: repeated presses kept moving focus to the next/previous grid item (as if the list were strictly single-column) rather than reaching the sidebar, even from the top row, and cost a lot of scripted-testing time without resolving. Possibly related to the already-documented HID coalescing artifact, possibly a real quirk in how the fixed 6-column `LazyVGrid` interacts with the sidebar `TabView` at this simulator's effective render size — not concluded either way. Don't sink more time into blind D-pad path-finding here in a single session; if this needs testing, relaunch with `Left` from the tab bar (known reliable) into the target grid cell rather than trying to navigate back out to a different tab from deep in the grid.

**Bug #2 recurs anywhere the same pattern is copy-pasted — it did, at the dialog buttons.** `pageJumpCard`'s and `nextComicConfirmation`'s Annulla/confirm buttons were added without their own `.focused(...)` binding, so the exact same nil-reversion problem showed up there too: reaching those buttons via ordinary navigation reverted `readerFocus` to `nil`, and the pager (still checking `readerFocus == nil`) silently regained focusability underneath the open dialog. Fixed the same way — `.dialogCancel`/`.dialogConfirm` cases shared by both dialogs (only one is ever on screen at once, so they don't need distinct cases per dialog) — plus setting `readerFocus = .dialogCancel` explicitly at the same call site that sets `pendingNextComic`, mirroring the header's Up-case fix (relying on the system's default-focus search after a `.focusable` flip was already shown to be unreliable once, no reason to trust it here). **The actual lesson: audit every `.focusable`-gated view that shares a `readerFocus`-style enum, not just the one you're currently debugging — this class of bug hides wherever a new focusable button gets added without a matching binding.**

**Don't drop the `nil` case from an `isPagerFocusable`-style check to fix bug #2 — that breaks initial focus instead.** Tried `readerFocus == .pager` (no `nil`) as a stricter fix; it built and even looked more "correct" as English, but broke page-turning on every fresh mount — confirmed via the same print+log method that `step()` was never being called after a clean launch. Cause: `readerFocus` really is `nil` for one real frame before `onAppear` sets `.pager`, and making the pager `.focusable(false)` during that frame is enough for tvOS to commit its one-time initial-focus decision to a different on-screen button (a header icon) before the pager's `.focusable` flips true a moment later — and focus doesn't retroactively transfer just because a view becomes focusable after the fact. `readerFocus == nil || readerFocus == .pager` is correct specifically *because* bug #2 is now fixed everywhere (every real button has its own binding, so `nil` can no longer mean "focus is legitimately elsewhere") — the two fixes depend on each other; don't ship one without the other.

Fix: don't just toggle a `Bool`/reassign a `@FocusState` binding's value and hope the system re-targets focus — make `.focusable` on the view you're leaving *itself* depend on where focus should be, so the system is forced to hand off real UIKit focus:
```swift
private enum ReaderFocusTarget: Hashable { case pager, header }
@FocusState private var readerFocus: ReaderFocusTarget?
private var isPagerFocusable: Bool {
    readerFocus != .header && !(/* any dialog conditions */)
}
// on the pager:
.focusable(isPagerFocusable)
.focused($readerFocus, equals: .pager)
.onMoveCommand { direction in
    if direction == .up { readerFocus = .header }   // triggers isPagerFocusable → false → real focus hand-off
}
// on the header's first button:
.focused($readerFocus, equals: .header)
```
Verified live end-to-end: Up → Right no longer turns the page (confirmed by page label staying put) → Select opens the search view (confirmed by its own UI, e.g. "Cerca nel fumetto" field, actually appearing) — not just "focus reached somewhere," the full path to a second header icon now works.

**Debugging method that actually worked, for next time:** black-box screenshot/snapshot-based inference was not enough to root-cause this (it kept producing self-contradicting evidence — e.g. "the page never turns" turned out to be because testing happened to be at the last page, where turning is a no-op regardless of focus). Adding temporary `print("MARKER ...")` statements at the specific decision points in question, then `build_run_sim`, reproducing, and `grep`ing the returned `runtimeLogPath` gave an unambiguous, ordered trace of exactly which closures fired — this is the reliable way to settle "is focus really moving" questions on tvOS, not screenshots. Remove the prints once the real mechanism is confirmed.

**A focused `Button` does not reliably give up real UIKit focus even when `.focusable` toggles false — the `isPagerFocusable` trick above only works because the pager isn't a `Button`.** The reverse direction of the header/pager fix (Down, from a header `Button` back to the pager) kept failing even after applying the identical `.focusable(readerFocus != .pager)` + `.focused($readerFocus, equals: .libreria)` pattern that already worked for the pager. Confirmed live, four different ways, that the button never actually released focus: (1) plain state reassignment — `readerFocus` visibly changed in the log but a subsequent Left press still fired the *same* button's own `.onMoveCommand`, and a stray Select press fired the button's own action (a library pop), not the pager's; (2) `.disabled(readerFocus == .pager)` instead of `.focusable` — broke Up-reachability too, since a Button disabled from the start is invisible to the initial directional focus search; (3) clearing `readerFocus` to `nil` then reassigning `.pager` on the next run-loop tick (`DispatchQueue.main.async`) — the closure demonstrably ran (logged), but the button still kept receiving move commands afterward; (4) `.id(readerFocus == .pager)` on the header to force full view-identity recreation on the transition — still no hand-off, and it introduced its own churn (an extra spurious `nil` reassignment) on the *other* direction (pager → header) that had been working fine. Converting the button to a plain non-`Button` view (mirroring the pager exactly: `.contentShape(Rectangle()) + .onTapGesture` instead of `Button(action:)`) fixed the give-up-focus problem but broke *reachability* — Up from the pager could no longer find it at all, reproduced 3x, because a plain view that starts `.focusable(false)` isn't part of the tree the one-time initial-focus search considers, unlike a disabled/hidden `Button` which apparently still is.

**The "hidden nav bar breaks Menu" bug (first found on `TVComicDetailView`) recurs on every screen pushed from the Account tab's own `NavigationStack`, not just that one.** `AccountsView.tvOSAccountList` is its own `NavigationStack` (the tvOS "Account" tab's root — nothing above it supplies one) and hides its nav bar the same way the library grid/detail pair originally did. Every one of its pushed destinations — `DownloadsView`, `LocalUploadView`, `RemoteBrowserView` (including its own recursive subfolder pushes), and `AddAccountView` (×3 entry points, one view) — inherited the same missing-affordance problem: with no visible bar anywhere in the stack, Menu falls through to exiting the *entire app* to the tvOS Home Screen instead of popping one level. Reproduced live for `DownloadsView` first (a single Menu press from its empty state landed on the Home Screen, confirmed via screenshot — app icons, not the Account list), then confirmed the same root cause applies structurally to the other three by inspection (identical unguarded push under the same hidden-bar `NavigationStack`) and live-verified the fix on three of the four (`DownloadsView`, `LocalUploadView`, `AddAccountView`; `RemoteBrowserView` needs a saved account to reach, blocked by the on-screen-keyboard limitation documented elsewhere in this file — not independently re-verified live, but it received the identical fix). Fixed the same way as `TVComicDetailView`: an explicit `.onExitCommand { dismiss() }` on each destination.

**That fix alone wasn't enough for a screen that can end up with *nothing* focusable — `.onExitCommand` needs a real focus target to ever fire.** `DownloadsView`'s empty state has no list rows and a `.disabled` "Stop all" button, and `.onExitCommand { dismiss() }` added there kept exiting the whole app anyway — confirmed via a temporary `print()` inside the closure (the standard debug method for this class of bug in this codebase) that it never fired at all. Two things turned out to be true, discovered in this order: (1) a `.disabled` `Button` cannot be forced focusable on tvOS by any `.focusable(true)` modifier placement (tried both before and after `.disabled` in the chain — neither worked, confirmed live each time); (2) once verified the ACTUAL fix (`.focusable(true)` on the screen's own outer container, a plain `TVPanel`/`VStack`, not a `Button`) does work, a misleading signal wasted real debugging time getting there: the currently-selected tab bar item stays highlighted white in a screenshot *regardless of where real focus actually is deeper in that tab's content* — it is NOT a reliable proxy for "focus is on the tab bar," and several intermediate fix attempts were wrongly declared failures based on that screenshot alone, without actually pressing Menu and checking the real resulting screen. **Lesson: for tvOS focus questions, the tab bar's highlight state proves nothing about where real focus is — always confirm by performing the actual action (here, pressing Menu and checking the destination screen) rather than reading a focus-adjacent visual cue.** The final, verified-live fix is just two modifiers on the screen root, no change needed to the list/button content underneath:
```swift
TVPanel(title: "Downloads") { EmptyView() } content: { downloadList }
    .focusable(true)
    .onExitCommand { dismiss() }
```

**Self-inflicted regression, found and fixed the same session: the Left/Right page-turn proxy above broke normal Right-navigation between header icons.** The first version of `handleHeaderMoveCommand` called `step()` for *every* Left/Right press unconditionally. This assumed `.onMoveCommand` only fires when the focus engine has nowhere else to go — wrong: it fires on every directional press as long as the view holds real focus, *regardless* of whether the system's own focus navigation also succeeds for that same press (already suspected from an earlier note in this doc — "`.onMoveCommand` kept firing on the pager as long as it stayed `.focusable(true)`" — but the implication for Left/Right specifically wasn't followed through at the time). Consequence, reproduced live: pressing Right from "Libreria" to reach the search icon *also* silently turned the page — invisible until it happened to be the last page, which instead popped the "Fine del fumetto" end-of-comic dialog. Fixed by gating the proxy behind a plain `@State private var isAwaitingPagerReturn: Bool`, set `true` only by the `.down` case and `false` by `.up`, so Left/Right only page-turn after an explicit Down — normal icon-to-icon Right/Left navigation (which the system's focus engine already handles correctly on its own) is untouched. **Lesson: don't assume `.onMoveCommand`'s firing conditions from how a bug *feels* like it should work — the pager's own doc comment nearby already had counter-evidence for exactly this behavior.** Also: Swift's `case .left, .right where isAwaitingPagerReturn:` only attaches `where` to the *last* pattern in the list (`.right`), not both — caught by a compiler warning, not by testing; write it as two separate `case` lines instead of relying on a shared `where` across a comma list.

**A `ContentUnavailableView` inside a `VStack(alignment: .leading)` hugs the leading edge instead of centering.** `LibraryView.swift`'s `content` shows `emptyState`/`noResultsState` (both plain `ContentUnavailableView`s, no explicit frame) when there are no comics/no matches. On tabs with a title row (`titledContent`'s `if let title = tvOSLibraryTitle` branch — true for "Preferiti", any series group, but *not* the plain "Libreria" tab), that content sits inside `VStack(alignment: .leading, spacing: 0) { Text(title); content }`. A `ContentUnavailableView` has no inherent width/height — it sizes to fit and, with no frame of its own, aligns to the VStack's `.leading` edge rather than centering across the remaining screen. Reported live by the user testing the Preferiti empty state (`docs/tvOS-coverage-checklist.md`'s "empty state" entry): the "Nessun preferito" card sat in the top-left corner instead of centered. `libraryGrid` itself wasn't affected — it's already a `ScrollView` that fills the available width on its own. Fixed by giving `content`'s empty/no-results branches an explicit `.frame(maxWidth: .infinity, maxHeight: .infinity)`, so they claim the full remaining space and `ContentUnavailableView`'s own internal centering applies to the whole screen, not just its intrinsic size. Verified live after the fix: card centers correctly, no regression to the grid's own scrolling/layout.

**Working fix: stop trying to force real focus transfer off the Button — proxy the directional input functionally instead.** Since every header button already receives `.onMoveCommand` for as long as it holds real focus (confirmed by all four failed attempts above — the handler reliably *fires*, it's only the focus hand-off that fails), the pragmatic fix has that same handler perform the Left/Right page-turn directly, without waiting for focus to actually relocate:
```swift
private func handleHeaderMoveCommand(_ direction: MoveCommandDirection) {
    readerFocus = .pager   // best-effort, kept for whenever the platform does honor it
    guard let provider else { return }
    switch direction {
    case .left: step(-1, provider: provider, style: tapPageTurnStyle)
    case .right: step(1, provider: provider, style: tapPageTurnStyle)
    default: break
    }
}
// every header Button:
.onMoveCommand(perform: handleHeaderMoveCommand)
```
Verified live end-to-end: from the header (Libreria button focused, confirmed via log), pressing Left turned the page (`3 / 3` → `2 / 3`, confirmed by the on-screen page counter, not just a log line), and Right turned it back. The focus ring may stay visually on the header button — a real UIKit focus limitation, not a state bug — but the reported symptom ("can't get back down and keep navigating") is fully resolved functionally. Applied identically to all 6 header buttons via the one shared function, not just the one being tested.

**A Bonjour-discovered SMB server's host string can carry a `%en0`-style interface zone suffix that breaks the connection outright — strip it for IPv4.** Found live testing against the user's real NAS (first time this app's SMB code had ever been exercised against a real server, not a placeholder address): selecting the "Trovati in rete" entry auto-filled `192.168.1.10%en0` into Indirizzo, and every connection attempt (speed test, the new "Sfoglia condivisioni") failed. Root cause: `SMBDiscoveryService.hostString(from:)` builds the address via `"\(address)"` on the resolved `NWEndpoint.Host`'s `IPv4Address` — its `description` appends the resolving interface as a zone suffix whenever the endpoint was reached over a specific interface, which `NWConnection`'s Bonjour resolution path does. `SMB2Manager`/AMSMB2 then rejects that suffix outright (not valid IPv4 or hostname syntax for any normal consumer). Fixed by splitting on `%` and keeping only the address portion, IPv4 only — IPv6 keeps its zone as-is since a zone ID is genuinely part of a link-local IPv6 address's identity, unlike IPv4 where it's purely a Swift-description artifact. Verified live end-to-end after the fix: the same discovered server now shows a clean `192.168.1.10`, and a real `listShares()` call against it (see the "Sfoglia condivisioni" feature note) returned the server's actual shares.

**Packing multiple `.buttonStyle(.card)` buttons into one `Form`/`List` row is a third source of the nested-shape bug — the row itself, not code we wrote, supplies the second shape.** Reported live by the user with a screenshot ("qua c'è il doppio cerchio") on `ColorThemeView`'s "Tint pagina" section: focus "Notte" and two overlapping rounded shapes are visible, even though `tintPresetButton` adds no background of its own on tvOS (`#if !os(tvOS)` gates its only `.background`/`.cornerRadius`) — unlike the two previously-documented causes (an extra `Capsule()`/`Circle()` background we added, or a bound view's own removal), this one comes from the *row*: three `Button`s share one `HStack` inside a single `Form` `Section` row, and tvOS gives that row its own default background sized to the whole row — a different footprint than each button's own `.card` fill, so the row's background peeks out from behind whichever button is focused. **Dismissing a `.focused($x, equals:)`-bound `Button` can silently overwrite an explicit reassignment of `x` made in the same action closure, landing real focus on the wrong sibling.** Found live while re-testing the reader's end-of-comic dialog after the floating-pill redesign: trigger "Fine del fumetto" → select "Annulla" → the dialog closes correctly, but a subsequent Left/Right press does nothing at all — no page turn, and (confirmed by temporary `print()` tracing, the established method for this class of bug in this file) `step()`/`nextComicInLibrary` never even got called. `nextComicConfirmation`'s Annulla action already did the established-correct thing, `pendingNextComic = nil; readerFocus = .pager`, both in one synchronous closure — but the trace showed `readerFocus` passing through `nil` (not `.pager`) right after, then settling on `.libreria` (or, in another run, `.layout`) — i.e. on whichever header button ends up nearest once the framework picks a real replacement, not on the pager we explicitly asked for. **A plain top `TabView` above a `ScrollView`/`LazyVGrid` can get focus stuck on the tab bar, unable to return Down into the grid — fix with `.focusSection()` on the scrollable content.** Reported by the user, reproduced consistently on the simulator (not a one-off input flake — same repro succeeded every time before the fix, failed every time after): scroll down into the library grid (tab bar auto-hides, standard behavior), press Up enough times to reach the tab bar, then press Down — focus stayed on the tab bar instead of returning to the last-focused cell, so the bar could never scroll back out of the way again. `LibraryView.swift`'s `libraryGrid` had no focus-region boundary between the tab bar (owned by `TVRootTabView`'s native `TabView`) and its own `ScrollView` — nothing in this app's code customizes that boundary anywhere else either (grepped, zero prior use of `.focusSection()`/`.prefersDefaultFocus`/`.defaultFocus` in the codebase). `.focusSection()` on the `ScrollView` is Apple's own documented tool for exactly this "content region below/beside another focusable region" shape — marks the grid as a distinct area so the focus engine's directional heuristics between it and the tab bar work reliably. ## Theming

**A custom `theme.text`/`theme.background` combined with a *different*, independently-forced `colorSchemeMode` makes system `.secondary`/`.primary` render unreadable — confirmed live, caught from the user's own screenshot ("qua manca il contrasto") while producing README screenshots.** `AppTheme.colorSchemeMode` (Automatica/Chiara/Scura) and `AppTheme.background`/`.text` (custom hex colors) are independent settings — nothing keeps them coordinated. With `colorSchemeMode = .dark` (forces `.preferredColorScheme(.dark)` app-wide) but a light custom `background` (`#F4ECD8`, cream) and a dark custom `text` (`#3B2F1E`, brown) — a real, easily-reachable combination, not a contrived edge case — `LibraryView`'s section headers ("NOVITÀ", "6 fumetti", "TUTTI I FUMETTI (N)") were nearly invisible: light-gray-on-cream instead of the intended dark brown. Root cause, found by reading the code rather than guessing from the visual symptom: `sectionHeaderContent`'s `Text("\(comics.count) fumetti")` (and its siblings) used the system `.foregroundColor(.secondary)` instead of deriving from `theme.text` — `.secondary` is computed from `colorSchemeMode`, blind to the custom palette entirely. Worse, `sectionHeaderContent`'s enclosing `HStack` also had an explicit `.foregroundColor(.primary)`, which — being *closer* to the section title `Text` than the `theme.text` applied much higher up in `LibraryView`'s own body — won and overrode the correctly-inherited custom color with the system one, making even the plain title text (no `.secondary` involved) render in the wrong color. Fixed two ways: (1) added `AppTheme.secondaryText` (`text?.opacity(0.6)`, nil when no custom text color is set so the system-`.secondary` case is unaffected) and used it everywhere `LibraryView` used bare `.secondary` — the section count labels and the alphabetical-mode "TUTTI I FUMETTI" header; (2) removed the stray `.foregroundColor(.primary)` override entirely, letting the section header inherit `theme.text` like the rest of the screen already does. Verified live: rebuilt the exact same theme preferences (cream background + dark-brown text + dark colorSchemeMode) into a clean simulator container and confirmed both labels now render in readable dark brown, matching the rest of the screen.

## Layout

**`.buttonStyle(.card)`'s cover, sized purely by `.aspectRatio(...).frame(maxWidth: .infinity)`, shrinks to make room when a *sibling* title text in the same `VStack` wraps to more lines than its row neighbors — confirmed live from the user's own screenshot ("non hanno la stessa altezza le copertine").** `LibraryView`'s tvOS grid cell (`cellButton`) is `VStack { Button(cover).buttonStyle(.card); Text(title).lineLimit(2) }`, with no explicit height reserved for the title block — it's exactly as tall as however many lines (1 or 2) the actual title needs. In a `LazyVGrid` row where one cell's title wraps to 2 lines and its neighbors' don't, the row's shared height ends up governed by the tallest cell, and the 2-line cell's own cover shrinks to keep that cell's total height in budget — reproduced live with "Temple of the Lost King" (2-line title) visibly shorter than its 1-line-titled neighbors in the same row, confirmed by screenshot (top edges aligned, bottom edges not). Fixed by reserving the title block's height unconditionally at two lines, independent of the actual title's length — the standard SwiftUI ghost-text trick: a `Text("Two\nLines").opacity(0)` in a `ZStack` behind the real (possibly 1-line) title, both under one shared `.font(...)`. This makes every cell's title block the same height regardless of content, so the row height is never driven by title-length variance and the cover never needs to compensate. Verified live: rebuilt the same 6-comic library (including "Temple of the Lost King") and confirmed all 6 covers in the row now share the same height, top and bottom edges aligned.
